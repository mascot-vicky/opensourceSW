# 카탈로그 팀 전달과 추천 후보 기준

관련 작업: [Issue #27](https://github.com/seoJing/opensourceSW/issues/27) · 기준 데이터: `haenggung-2026-11-18.2` · 상태: 맛 기반 MVP 방향 반영·속성 상세는 검토안

이 문서는 [출처와 입력 기준 PR #25](https://github.com/seoJing/opensourceSW/pull/25)의 실제 카탈로그를 팀원이 **동일한 실행 입력으로** 받는 절차와 추천 후보를 고르는 기준을 정한다. 원자료를 다시 수집하는 절차는 포함하지 않는다. 회의에서 정한 맛 기반 추천 방향을 반영하며 점수 공식·HTTP 필드·속성 목록은 확정 계약과 구분한다.

## 1. 전달 단위

다른 사용자는 버전별 압축 파일 `haenggung-2026-11-18.2.tar.gz`를 자신의 PC에 받아 사용한다. 전달 매체는 직접 파일 전달이나 접근을 제한한 공유 공간 등으로 선택할 수 있다. 특정 공유 서비스·사용자 계정·PC 접근은 실행 구성의 전제가 아니다. 묶음에는 아래 세 파일만 넣으며 실제 자료는 Git 저장소에 추가하지 않는다.

| 파일 | 용도 |
| --- | --- |
| `catalog.json` | 백엔드 로더가 읽는 카페·메뉴 입력 |
| `manifest.json` | 데이터 버전, 수량, 카탈로그 SHA-256과 수집 범위 |
| `SHA256SUMS` | 받은 두 파일의 바이트 동일성 검사 |

검토용 원문, 수집 스크립트, `review-decisions.json`, API 자격 증명, 세션 정보는 실행 묶음에 넣지 않는다. 이 묶음은 **검토된 입력을 재현**하게 하며, 원천 페이지의 현재 상태나 재수집 결과가 같음을 보장하지 않는다. 공유 위치와 수신자는 실제 전달할 때 정한다.

제공자는 고정된 버전 폴더에서 다음처럼 묶음을 만들고, 압축 파일의 SHA-256을 팀 내부 전달 메시지에 함께 적는다. 파일을 수정했다면 `dataVersion`과 묶음 이름을 함께 바꾸고 다시 검증한다.

```sh
cd /path/to/haenggung-2026-11-18.2
sha256sum catalog.json manifest.json > SHA256SUMS
tar -czf ../haenggung-2026-11-18.2.tar.gz catalog.json manifest.json SHA256SUMS
sha256sum ../haenggung-2026-11-18.2.tar.gz
```

수신자는 공유 메시지의 압축 파일 해시를 먼저 대조한 후 빈 버전 폴더에 풀고 파일별 해시를 검사한다. 압축 파일의 해시와 `SHA256SUMS`가 모두 같아야 한다.

```sh
sha256sum haenggung-2026-11-18.2.tar.gz
mkdir -p haenggung-2026-11-18.2
tar -xzf haenggung-2026-11-18.2.tar.gz -C haenggung-2026-11-18.2
cd haenggung-2026-11-18.2
sha256sum -c SHA256SUMS
```

위 해시 명령은 WSL·Linux 기준이다. macOS에서는 `shasum -a 256`과 `shasum -a 256 -c SHA256SUMS`, Windows PowerShell에서는 `Get-FileHash -Algorithm SHA256`으로 같은 값을 확인한다. 두 환경 모두 `tar -xzf`로 압축을 풀 수 있다. 호스트의 파일 경로를 Docker 컨테이너 내부 경로로 그대로 넘기지 않는다.

이 버전의 `manifest.json`에는 `catalogSha256=77101fe31346de40225d23adca5a485f74cb4861e98a9a8e9d1cf7474ab4eb0d`, 카페 320곳, 입력 메뉴 5,011건이 기록되어 있다. `catalog.json`의 `dataVersion`도 묶음 이름과 일치해야 한다. 체크섬을 통과해도 로더 검증을 생략하지 않는다. #22 로더로 스키마·참조를 검사하고, #24가 병합된 뒤에는 `APP_CATALOG_ENABLED=true`, `APP_CATALOG_PATH`를 지정해 시작 시 PostgreSQL에 적재한다. 같은 버전·같은 SHA-256은 중복 저장하지 않고, 같은 버전의 다른 바이트는 거부한다. 새 버전은 별도 폴더에 풀어 검증한 뒤 경로를 바꾼다. 직접 실행한 JVM은 재시작하고, Docker의 호스트 파일 연결을 바꿀 때는 [PR #30 실행 안내](https://github.com/seoJing/opensourceSW/pull/30)에 따라 백엔드 컨테이너를 다시 생성한다. 문제가 있으면 이전 경로로 같은 절차를 적용한다.

현재 `main`의 Compose에는 JSON 파일 마운트나 카탈로그 DB 적재가 없다. PostgreSQL의 `postgres_data` 볼륨은 DB 파일을 지속시키지만 JSON을 자동으로 적재하지 않는다. 팀 시연에서 실제 자료를 컨테이너에 공급하기 위한 읽기 전용 연결은 [Draft PR #30](https://github.com/seoJing/opensourceSW/pull/30)에서 준비했다. 프론트 Nginx도 현재 `/api/health`만 백엔드로 연결하므로 기능 API 프록시는 별도 작업이다. Issue #24는 **JSON을 전달 원본으로, PostgreSQL을 조회 저장소로** 사용한다. 전체 저장과 활성 버전 전환을 한 트랜잭션에서 처리하며, 이전 버전은 보존한다. 적재 후 파일 연결을 해제해도 DB 데이터는 유지된다. DB 구현은 #24, 외부 파일 연결은 #29가 담당하며 이 문서는 전달·후보 기준을 다룬다.

## 2. 추천 후보 판정

`catalog.json`은 카페 320곳과 메뉴 5,011건을 보관하지만, 이 수가 추천 가능한 메뉴 수는 아니다. 원문 5,020건 중 9건은 입력 전에 보류됐고, 입력 메뉴 중 40건은 `SEASON_ENDED`다. 나머지 4,971건은 `UNKNOWN`으로, **현재 판매가 확인된 메뉴는 0건**이다. 메뉴 227건의 가격, 2,275건의 설명도 비어 있다.

| 단계 | 기준 | 처리 |
| --- | --- | --- |
| 자동 제외 | `isDemo=true`, `UNAVAILABLE`, `SEASON_ENDED` | 추천 후보에서 제외. 원본 카탈로그에서는 삭제하지 않음 |
| 검토 대기 | `UNKNOWN` | 판매 확정으로 표기하지 않음. 현재 4,971건은 이 단계에서 시작 |
| 항목 분류 | 음료·디저트·베이커리처럼 실제 메뉴인 항목 | 메뉴명·설명·출처에 근거해 분류. 안내·선물·주류는 제외하고, 같은 매장의 중복 의심·분류 불명 항목은 검토 대기 |
| 가격 | 모든 가격 값 | 추천 점수·필터에서 제외. 원본은 보존하며 화면 표시 시 미확인을 0원으로 바꾸지 않음 |
| 취향 속성 | 맛 속성만 사용 | 메뉴명·설명을 LLM 배치로 수치화하는 방향. 생성값은 원자료와 분리하고 0~1 범위·속성 버전을 검증. 재료·옵션·건강·인테리어는 이번 추천 조건에서 제외 |

이 규칙의 자동 제외 단계만 적용하면 4,971건의 **검토 대상**이 남는다. 카탈로그 v1에는 메뉴 분류·취향 태그가 없으므로, 이를 곧바로 최종 추천 후보라고 부르지 않는다. 추천 후보를 확정할 때는 별도 검토표에 `dataVersion`, `menuId`, `decision(INCLUDE/EXCLUDE/REVIEW)`, `category`, `reason`, `evidence`, `reviewedOn`을 남긴다. 분류 근거가 없는 메뉴는 `REVIEW`에 두며, 메뉴 페이지에 표시된 사실과 현재 판매 확인을 서로 다른 근거로 기록한다.

첫 시연에서는 검토가 끝난 메뉴만 추천 입력으로 사용한다. `availability=UNKNOWN`인 메뉴를 포함한다면 화면에는 판매 여부를 확인해야 한다고 표시한다. **판매 중이라고 단정하는 추천**이 필요하다면 해당 메뉴의 직접 확인 근거를 남기고 카탈로그 상태를 갱신해야 한다. 후보의 실제 개수와 카페·분류별 분포는 검토표가 완성된 뒤 기록한다.

설문과 메뉴는 같은 맛 속성 정의를 사용한다. 단맛·신맛은 후보로 확인했으며, 단맛·신맛·쓴맛의 3축은 초기 검토안이다. 최종 목록·각 값의 기준·질문별 변환은 확정 전이다. 메뉴 수치는 맛 강도, 사용자 수치는 원하는 맛 강도로 해석하는 안이며 추천 중요도와 구분한다. 중립 또는 미확인 값을 자동으로 0으로 채우지 않는다.

메뉴 수치 생성은 메뉴명·설명을 입력하는 LLM 배치로 준비한다. 결과는 측정값이 아닌 추정치로 기록한다. 원자료와 분리된 결과에 카탈로그·메뉴 ID, 속성 정의·모델·프롬프트 버전과 생성 이력을 연결하는 방향이며 아직 구현하지 않았다. 구조·범위 검사와 대표 메뉴 검토를 통과한 결과를 DB에 저장한다. 요청 시에는 DB의 검증된 수치를 사용한다.

질문 확정은 속성 정의 이후에 진행한다. 초기 설문으로 사용자 수치를 만드는 기능은 구현 대상이고, 카드 선택에 따른 추가 학습은 발표에서 확장 가능성으로 설명한다. 추천 메뉴 응답에 카페 이름·주소·네이버 지도 길찾기 URL을 포함해 카드 선택 시 서버를 다시 호출하지 않는 방향이다. 지도 내장, 가격·인테리어 평가, 리뷰 수집은 이번 MVP 범위에서 제외한다. 카드 목록 또는 한 장 반환 여부와 HTTP 필드명은 프론트와 확정해야 한다.

## 3. 이번 검증과 남은 결정

2026-11-18에 세 파일을 로컬 묶음으로 만들고 다른 폴더에 추출했다. `sha256sum -c`가 두 파일 모두 통과했고, `manifest.json`의 버전·카페·메뉴 수·카탈로그 해시가 추출 파일과 일치했다. #22의 Java 로더는 추출된 JSON에서 카페 320곳·메뉴 5,011건을 읽었다. **다른 팀원 PC에서 공유·실행한 결과는 아직 없다.**

추천 연결 전에는 맛 속성과 기준값·질문별 변환·LLM 생성 형식·비교식·최초 후보 범위·`UNKNOWN` 메뉴의 표기를 확정해야 한다. PostgreSQL 적재는 PR #31, 파일 연결은 PR #30에서 담당하며 두 구성을 함께 실제 Docker에서 실행해 데이터 적재와 볼륨 보존을 검증했다. LLM 수치 저장과 추천 계산은 아직 구현되지 않았다. 이번 이식성 작업은 전달 형식·체크섬·외부 경로 설정·실행 안내를 갖추는 범위이며, 특정 사용자 PC의 접속이나 실제 전달 완료를 요구하지 않는다.
